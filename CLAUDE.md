## Architecture cible

Deux blocs, **un seul déploiement** :

- **Frontend** : SPA React 19 + TypeScript, build Vite, installable en PWA. Servie en statique par PocketBase depuis `pb_public/` — donc **pas de CORS et pas de serveur frontend séparé**.
- **Backend** : PocketBase (binaire Go unique) fournissant SQLite, l'auth e-mail/mot de passe, l'API REST/Realtime et l'admin. La logique métier serveur s'écrit en hooks JS dans `pb_hooks/`.
- **Sauvegarde** : Litestream réplique en continu le fichier SQLite vers Hetzner Object Storage (S3).

Layout du monorepo : `frontend/`, `packages/domain/`, `pb_hooks/` et `pb_migrations/` existent ; `deploy/` porte le mode opératoire, le fichier Compose et l'entrypoint ; le `Dockerfile` est à la racine.

`packages/domain` étend le layout des specs : il porte les calculs financiers en TypeScript pur, sans dépendance à React ni à PocketBase, pour être partagé entre le frontend et les hooks serveur (compilé en CommonJS vers `pb_hooks/lib/` à partir de l'étape 2). Les hooks se limitent à l'orchestration.

### Répartition client / serveur

Cette frontière est une décision d'architecture, pas un détail :

- **Côté serveur (hooks PocketBase)** : mise à jour de `debts.remaining_amount` sur création/modification/suppression d'un `debt_payment`, génération des transactions récurrentes (cron quotidien 06:00), notifications d'échéance J-3/J-1/J, alertes de dépassement de budget à 80 % / 100 %, reports `carry_over` et clôture mensuelle (cron le 1er), envoi des e-mails.
- **Côté client (calcul pur)** : simulateurs de remboursement anticipé et comparaison « boule de neige » vs « avalanche ». Aucun aller-retour serveur.

### Soldes et cumuls

Les soldes de comptes et les cumuls budgétaires sont **calculés à la volée** (somme des transactions), jamais stockés dénormalisés. Les index SQLite `(user, account, date)` et `(user, category, date)` portent cette approche. Ne pas introduire de colonne de solde matérialisée sans revenir sur cette décision.

## Conventions non négociables

- **Code intégralement en anglais** : identifiants, noms de fichiers, noms de tests, champs de collections, messages de commit. Seul le texte affiché à l'utilisateur est en français.
- **Commentaires parcimonieux** : on commente le _pourquoi_ d'une décision non évidente, jamais le _quoi_. Un commentaire qui paraphrase le code est supprimé.
- **Versions de librairies** : toujours vérifiées via `ctx7` (doc) et le registre npm (version publiée) avant installation, jamais de mémoire. Les versions des specs datent du 09/08/2026 et servent de plancher, pas de vérité.
- **Montants : entiers XOF, sans décimales.** Aucun flottant pour un montant, nulle part — ni en base, ni en TypeScript, ni dans les calculs de simulateur. Affichage via `Intl.NumberFormat('fr-FR', { currency: 'XOF' })` → `150 000 F CFA` (séparateur de milliers : une espace insécable, voir la section Tests).
- **Isolation par utilisateur** : toute collection PocketBase porte un champ `user` (relation vers `users`) et des règles d'accès `user = @request.auth.id`. Une nouvelle collection sans cette règle est un bug de sécurité.
- **Mois budgétaire = mois calendaire**, du 1er au dernier jour, non paramétrable en v1. Les budgets sont clés par `month` au format texte `YYYY-MM`.
- **Langue** : interface en français uniquement en v1 (`date-fns` en locale `fr`).
- **Mobile-first** : la cible principale est le mobile ; tablette et desktop suivent. Objectif de saisie d'une transaction : moins de 10 secondes (`TRX-01`).
- **Accessibilité** : WCAG AA visé (contrastes, navigation clavier, libellés de formulaires explicites).

## Tests

Deux niveaux, sans couche intermédiaire de tests de composants.

- `packages/domain/**/*.test.ts` — projet Vitest `domain`, en node. Uniquement les règles métier à risque financier : arithmétique XOF, échéanciers, répartition capital/intérêts, seuils de budget. Style BDD : `describe` porte le contexte (« Given… »), `it` porte le comportement observable.
- `frontend/**/*.journey.tsx` — projet Vitest `journeys`, en browser mode chromium via `vitest-browser-react`. L'application réelle est montée contre une instance PocketBase de test, **sans mock du SDK** : ces parcours couvrent aussi les règles d'accès et les hooks serveur. `render()` est asynchrone, il faut l'`await`.

On n'écrit pas : tests de composants de présentation, snapshots, tests de getters, ni tests qui mockent la couche qu'ils prétendent vérifier. Un test qui ne peut pas échouer sur une régression métier réelle n'a pas sa place.

Piège vérifié : `Intl` formate les montants XOF avec des espaces insécables (U+202F, U+00A0) dont les points de code dépendent de la version d'ICU embarquée dans Node. Les assertions de format utilisent `\s`, jamais un espace littéral.

## Authentification

- PocketBase **fournit déjà** une collection `users` dont les règles d'accès sont `id = @request.auth.id`. La migration `pb_migrations/1786404350_extend_users_collection.js` ne fait qu'ajouter `settings` et relever le plancher de mot de passe de 8 à 10 (specs §5). Ne pas recréer cette collection.
- Le routage est **par code** (`frontend/src/router.tsx`), pas par fichiers : à l'échelle prévue, le plugin et le `routeTree.gen.ts` ne s'amortissent pas. `createAppRouter(history?)` accepte un historique mémoire, ce dont les parcours se servent.
- La garde d'accès lit `pb.authStore.isValid` directement dans `beforeLoad`, sans passer par le contexte du router — une source de vérité unique, pas de synchronisation à tenir. Comme `beforeLoad` ne se rejoue qu'à la navigation, `AppRouterProvider` invalide le router à chaque changement de l'authStore : monter `RouterProvider` en direct rouvrirait le trou (session vidée dans un autre onglet, jeton expiré).
- `confirmPasswordReset` vide l'authStore après succès : PocketBase fait tourner le `tokenKey` au changement de mot de passe, donc la session locale est morte côté serveur tout en paraissant valide à la garde.
- **L'instantané de `useAuth` est `token|name`, pas le jeton seul** : le hook rend le nom, donc il doit observer le nom. Enregistrer un nom rafraîchit le record **sans** émettre de nouveau jeton, et `useSyncExternalStore` comparant deux instantanés identiques ne re-rendait rien. Une **chaîne** et jamais un objet — `getSnapshot` tourne à chaque rendu, et un objet neuf à chaque fois boucle. Vérifié discriminant par le seul chemin qui le prouve : remplacer le record **hors de l'arbre React** (`pb.authStore.save`), ce que le SDK fait lui-même à chaque rafraîchissement de session. Le test qui enregistre le nom depuis l'écran, lui, passe dans les deux cas — le re-rendu du parent suffit — et ne prouve donc rien.
- **`name` peut être périmé, l'adresse ne le pouvait pas.** Rien n'appelle `authRefresh()` : une session valide ouverte avant un changement de nom continue de saluer par l'adresse pendant que `/api/export` renvoie déjà le nouveau nom. Défaut connu, non corrigé — il partage son correctif avec la session révoquée qui affiche encore `0 F CFA`, et réfuter la session au démarrage touche la garde d'accès, donc cela demande son propre changement.
- **La salutation _et_ l'adresse vont ensemble, partout où va le bouton de déconnexion.** « Bon retour, &lt;Nom&gt; » sur une ligne, l'adresse sous elle. La salutation seule avait retiré la seule mention de quel compte est connecté, à côté du bouton de déconnexion — sur un appareil partagé, ou entre deux personnes portant le même prénom, plus rien ne disait quelles données ce bouton allait quitter. Les deux ont quitté l'en-tête pour le menu et le pied du rail à la PR 3/7 ; voir « Coque et navigation » pour ce que ce déplacement coûte.
- **Le brouillon du champ « Nom » se réaligne pendant le rendu, pas dans un effet.** Semé une fois, il gardait sa valeur de naissance : l'authStore porte dans cet onglet un nom enregistré dans un autre, l'en-tête suivait et le champ non, et enregistrer ici réécrivait l'ancien nom par-dessus le nouveau. Le compilateur React refuse un `setState` dans un effet (cascade de rendus) et un `key` sur le formulaire le remonterait — donc **perdrait le focus du bouton qu'on vient de presser**. Le motif retenu est l'ajustement d'état pendant le rendu, avec son `lastSeenName`.
- **Le second facteur est l'OTP par e-mail, et ce n'est pas un choix de confort.** Le MFA de PocketBase exige **deux de ses propres méthodes** et n'offre **aucun point d'extension** pour un facteur tiers ; côté hooks, `$security` donne `hs256`/`hs512` mais **pas HMAC-SHA1**, l'algorithme que Google Authenticator impose en ignorant le paramètre `algorithm` de l'URI `otpauth://`. Un TOTP maison serait soit un verrou client — le jeton étant déjà émis, le raisonnement qui a fait reporter `USR-05` —, soit une réécriture de l'émission de jetons sur le chemin de connexion.
- **`options.mfa.rule` vide signifie TOUT LE MONDE, pas personne.** Mesuré le 31/08/2026 en la vidant : l'inscription elle-même a cessé de fonctionner, la connexion qui suit l'enregistrement rencontrant un défi pour un compte qui n'avait rien demandé. `mfa_enabled = true` est ce qui fait du second facteur un choix et non un mur. Le drapeau est une **colonne booléenne**, jamais un chemin dans le JSON `settings` — un filtre sur un chemin JSON ne ramène rien ici, déjà mesuré.
- **Activer `otp` ouvre une connexion SANS MOT DE PASSE pour tout le monde.** L'OTP de PocketBase est une méthode d'authentification à part entière, pas un second facteur : `mfa.rule` rend une **seconde** méthode obligatoire pour les enregistrements qu'elle vise, et n'empêche nullement la première d'être le code lui-même. Comme `mfa_enabled` vaut faux par défaut, chaque compte gagnait ainsi une connexion au seul code — **silencieusement**, à la différence d'une réinitialisation de mot de passe qui fait du bruit en changeant le mot de passe et en tuant les sessions. `pb_hooks/otp_is_a_second_factor_only.pb.js` refuse tout `authWithOTP` sans `mfaId`. Livré tel quel dans la première version de cette fonctionnalité, trouvé en revue.
- **`changePassword` se réauthentifie, et c'est précisément l'appel que le second facteur intercepte** — donc la fonctionnalité était cassée pour les comptes ayant activé l'autre moitié du même changement : le mot de passe **était** modifié et l'écran annonçait un échec. Pire que le message : le SDK réécrit l'enregistrement à côté du jeton que la rotation vient de tuer, et `authStore.isValid` ne lit que l'expiration du JWT — la garde gardait donc quelqu'un dans une application qui répondait 401 à tout. **Toute réauthentification qui échoue vide l'authStore**, quelle qu'en soit la raison, et un second facteur dû rend `false` plutôt que de lever.
- **Désactiver le second facteur exige le mot de passe ; l'activer non.** Le retrait est ce qu'un intrus veut, et un clic sur une session ouverte suffisait — ce qui faisait de l'interrupteur le maillon le plus faible de ce qu'il protège. La vérification passe par `authWithPassword`, donc c'est le serveur qui tranche ; pour un compte encore protégé, l'appel revient en réclamant un code, ce qui **n'est pas un échec** : cela ne peut arriver qu'une fois le mot de passe accepté.
- **PocketBase répond à « mot de passe juste, second facteur dû » par le même 401 qu'à un mot de passe faux.** Seule la présence de `mfaId` dans la réponse les distingue. Un écran qui regarderait le statut seul enverrait quelqu'un réinitialiser un mot de passe qui marche.
- **Deux chemins d'identifiants tuent la session en cours**, pour la même raison que `confirmPasswordReset` : le changement de mot de passe fait tourner le `tokenKey`, et la confirmation d'adresse invalide **tous** les jetons. Le premier se réauthentifie aussitôt avec le mot de passe qu'on vient de choisir — être éjecté pour avoir réussi une action ordinaire est une punition ; la seconde vide l'authStore et renvoie à la connexion, puisque l'adresse a changé.
- **Le modèle `confirmEmailChangeTemplate` avait le même défaut que celui de la réinitialisation** et a reçu la même correction (`1787700000`) : anglais, et pointant sur `{APP_URL}/_/#/auth/confirm-email-change/{TOKEN}`. `verificationTemplate` porte encore ce défaut, non corrigé.
- **Les parcours qui lisent Mailpit filtrent par sujet, jamais par destinataire seul.** `authAlert` est **activé** et envoie « Login from a new location » à la même adresse : prendre `messages[0]` lit le mauvais courriel dès que la machine est rapide, et un test qui échoue une fois sur trois est pire qu'un test absent.
- Le client PocketBase pointe sur `VITE_POCKETBASE_URL`, avec `/` par défaut : en production PocketBase sert lui-même la SPA, donc même origine.
- Le modèle d'e-mail de réinitialisation est **remplacé par migration** : celui de PocketBase renvoie vers son interface admin (`{APP_URL}/_/#/auth/confirm-password-reset/{TOKEN}`), pas vers la SPA. Toute nouvelle collection auth aura le même défaut à corriger.
- **Le SMTP de production reste à configurer** (Brevo ou Resend, cf. specs §2.2). Sans lui, la réinitialisation de mot de passe ne fonctionne pas en production.

## Domaine partagé et moteur goja

`packages/domain` a **deux points d'entrée**, et la distinction n'est pas cosmétique :

- `src/index.ts` — tout, pour le frontend.
- `src/server.ts` — uniquement ce qui tourne sous PocketBase. C'est lui qu'on bundle.

**Le moteur goja n'a pas `Intl` du tout** (`ReferenceError: Intl is not defined`), et son `Number.prototype.toLocaleString` lit son argument comme un radix de `toString` : `(150000).toLocaleString('fr-FR')` lève une `RangeError`. Aucun formatage localisé n'est donc possible côté serveur. `src/format.ts` construit son `Intl.NumberFormat` au chargement du module : **l'ajouter à `server.ts` ferait planter les hooks au démarrage**. Quand un montant devra figurer dans un e-mail (étape 6), il faudra un formateur maison, testé.

Ce que goja accepte, vérifié à l'exécution : `class`, `const`, fonctions fléchées, `Number.isSafeInteger`. Le bundle cible donc **es2015**, pas l'`es5` annoncé par la doc — esbuild ne sait de toute façon pas abaisser `const` ni `class` jusqu'à es5.

Le bundle est en `platform: 'neutral'`, et ce n'est pas indifférent : sous `'node'`, esbuild externalise les modules natifs et émet des `require("node:fs")` que goja ne sait pas résoudre — l'erreur ne surgirait qu'à l'exécution. En `'neutral'`, importer un builtin **échoue au build**.

`pnpm domain:build` produit `pb_hooks/lib/domain.cjs` (CommonJS, es2015, fichier unique). L'extension `.cjs` est nécessaire : le `package.json` racine déclare `"type": "module"`, et l'outillage lirait sinon ce bundle comme de l'ESM. Les hooks l'importent par `require(`${__hooks}/lib/domain.cjs`)` — les chemins relatifs se résolvent depuis le répertoire courant, jamais depuis `pb_hooks`.

L'artefact est **généré et gitignoré**. Le harnais de test le **reconstruit lui-même** à chaque exécution (`buildDomain()` depuis `@budget/domain/build`) : s'en remettre à un hook `pretest` ne couvrait que `pnpm test`, et laissait `pnpm test:journeys` valider un bundle périmé en toute discrétion.

**La surface de `server.ts` est vérifiée par un test.** Les hooks appellent ce bundle depuis goja, sans types : une fonction absente du point d'entrée n'est une erreur de compilation nulle part, c'est un HTTP 400 sur ce que l'utilisateur était en train de faire. Mesuré une fois — un remboursement refusé parce que `splitPayment` n'avait jamais été exporté, pendant que tous les tests du domaine restaient verts en important le module directement.

**La marque `Money` disparaît à la compilation.** Les hooks appellent ce code depuis goja, sans types : toute fonction publique du domaine doit revalider ses entrées plutôt que se fier à sa signature.

**Chaque handler de hook est sérialisé et exécuté comme un programme isolé.** Il ne voit _rien_ de la portée du fichier : une `const` déclarée au-dessus de `onRecordAfterCreateSuccess(...)` y sera `undefined`, et l'erreur ne se manifeste qu'à l'exécution du hook, pas au démarrage. Les constantes vont donc dans le handler, et le code partagé passe par un `require()` **à l'intérieur** du handler.

## Comptes et catégories

- **La couleur est une clé de palette, jamais un hexadécimal** (`CAT-04`, `CPT-02`). Huit clés — `terracotta`, `ambre`, `olive`, `vert`, `sarcelle`, `indigo`, `prune`, `framboise` — définies dans `styles.css` et résolues par `frontend/src/lib/appearance.ts`. Un hexadécimal choisi sur le thème clair peut disparaître sur le sombre ; seule la feuille de style peut répondre pour les deux.
- **Une seule valeur par teinte pour les deux thèmes, et ce n'est pas une économie.** La fenêtre de luminance qui franchit 3:1 contre le blanc **et** contre `--k-surface` sombre va de 0,136 à 0,300 : elle existe, les huit s'y rangent. Leurs luminances y sont **étalées** plutôt qu'égales, pour garder 1,59:1 entre les extrêmes — un peu de séparation en niveaux de gris. C'est peu, et c'est pourquoi la couleur n'est jamais seule à porter : le nom est toujours à côté.
- **Tailwind lit le source comme du texte** : une classe construite en `bg-hue-${clé}` n'apparaît nulle part dans le fichier, donc rien ne la génère et la pastille sort transparente. `appearance.ts` porte une table clé → classe écrite à la main, et c'est la raison.
- **`accounts.color` existait depuis l'étape 3 sans qu'une seule écriture l'atteigne**, alors que `CPT-02` le réclamait depuis la première spécification. Troisième champ de ce dépôt dans ce cas, après `useUpdateTransaction` et `TransactionFilters.from/.to` — vérifier avant d'écrire.
- **Vide est l'état ordinaire, pas seulement l'état hérité.** Rien ne rétro-remplit les lignes antérieures à la migration `1788000000`, **et le formulaire ne présélectionne rien** : ce qui n'a pas été choisi est écrit `''`, donc le repli vit à un seul endroit au lieu d'être figé dans la ligne le jour de sa création. Toute lecture passe par `hueClassOf` / `iconOf`. La première version présélectionnait `terracotta` : toute catégorie et tout compte créés à la main sortaient de la même couleur, pendant que le hook de seed prenait soin de répartir ses teintes et que la dérivation prenait soin de les étaler. Une couleur qui ne distingue rien ne sert à rien.
- **Le formulaire dit ce qui arrive à défaut** (« Sans choix, elle est dérivée du nom »). Une grille où rien n'est coché sans un mot d'explication se lit comme un champ oublié.
- **La dérivation est stable, pas aléatoire** : la même chaîne rend toujours la même teinte. Une couleur qui bougerait entre deux rendus serait pire que pas de couleur.
- **`appearance.journey.tsx` est le seul parcours qui importe `styles.css`**, et il le fait pour la raison d'être de la palette : une teinte est une classe, donc une teinte que Tailwind n'a pas générée est un carré transparent et rien d'autre. Les parcours montent le routeur directement, jamais `main.tsx` — **ils tournent donc sans aucune feuille de style**, ce qui explique aussi pourquoi `axe-core` classe le contraste en « incomplet » plutôt que de le mesurer. Les assertions vont sur `getComputedStyle`, pas sur `className` : c'est ce qui distingue une classe absente d'une classe qui ne peint rien.
- **La première version de ce parcours ne pouvait pas échouer.** Elle comparait `hueFor(x)` à lui-même et vérifiait que `HUES` contient ce que `hueFor` en tire — deux tautologies. Mesuré : vider les deux replis de `hueClassOf` et `iconOf` laissait **324 tests sur 324 verts**. Une assertion d'apparence porte sur ce que la ligne dessine, jamais sur ce que la fonction rend.
- **L'icône se choisit dans une grille fermée**, jamais dans un champ libre : un caractère arbitraire est un carré vide sur une plateforme et trois colonnes de large sur une autre, et un champ qui accepte tout doit être validé pour quelque chose. Le repli est neutre (`🏷️`) et non deviné — aucune dérivation ne sait qu'une catégorie nommée « Coiffeur » veut un emoji précis, et un hachage dans la grille lui donnerait un taxi. **L'asymétrie avec la couleur est voulue et `CAT-04` la porte** : une teinte fausse ne dit rien de faux, une icône fausse si.
- **L'icône d'un compte est déduite de son type et ne se choisit pas** (`CPT-02`, `ACCOUNT_TYPE_ICONS`). Cinq types, ensemble fermé : le type dit déjà tout ce qu'une icône dirait, et offrir le choix ne ferait que permettre aux deux de se contredire. Le parcours vérifie **les deux moitiés** — que la ligne porte l'icône, et que le formulaire n'offre aucune grille « Icône ».
- **Le radio d'une pastille couvre la pastille, il n'est pas `sr-only`.** Clipé, il gardait une cible de 1×1 px dans le coin d'un carré de 44 px et ne fonctionnait que par délégation du label — invisible aux outils qui suivent la boîte de l'élément, et impossible à cliquer pour Playwright. `absolute inset-0 opacity-0` reste dans l'arbre d'accessibilité et rend la cible égale à ce que l'œil suit.
- **Ajouter l'icône a tronqué les noms à « Alim… » sur 390 px**, et les actions sont passées sur leur propre ligne — sur les catégories comme sur les comptes. Troisième fois que ce motif se produit après les transactions à l'étape 4 et à la PR #19 : **toute ligne de liste qui gagne un ornement à gauche doit être recapturée à 390 px**, aucune assertion ne le voit. **Quatrième fois aussitôt après** : l'icône de type a coûté aux comptes ce que le filet de couleur ne coûtait pas, « Compte courant BOA » redevenant « Compte couran… ». Le solde est descendu près du bouton — c'est la chose la plus large de la ligne et la seule qui ne tronque jamais. La capture se prend avec `page.viewport(390, 844)` dans un parcours jetable ; il n'en reste rien au dépôt.
- `accounts.initial_balance` est déclaré `onlyInt` : PocketBase refuse un montant fractionnaire en HTTP 400. L'invariant XOF tient jusqu'au stockage, pas seulement dans le domaine. Tout futur champ monétaire doit faire de même.
- Rien ne se supprime **tant qu'un historique y est attaché** : un compte s'archive (`archived`), une catégorie se désactive (`active`). En revanche une catégorie que **rien ne référence** se supprime — elle ne protège aucun historique, et la désactiver ne fait que la garder à l'écran pour toujours.
- **`pb_hooks/guard_category_deletion.pb.js` compte avant `e.next()`, jamais après.** `budgets.category` est la seule relation vers `categories` qui **cascade** : un garde-fou placé après aurait refusé la catégorie en ayant déjà détruit toutes ses enveloppes, mois passés compris, sans rien afficher. Le refus couvre les transactions, les enveloppes et les sous-catégories.
- **Une relation non cascadante ne protège rien quand le champ est optionnel.** Mesuré le 29/08/2026 en retirant le garde-fou : PocketBase répond 204 et **vide** la référence — `transactions.category` passe à `''`. Pas d'identifiant pendant, donc, mais une dépense qui perd sa catégorie en silence et sort des totaux budgétaires et de la répartition. Le cas des comptes se comportait autrement seulement parce que `transactions.account` est obligatoire.
- **Le garde-fou est branché sur `onRecordDeleteRequest`, pas `onRecordDelete`.** `categories.user` cascade aussi, et PocketBase exécute les hooks de modèle pour les enregistrements supprimés en cascade : sur le hook simple, fermer un compte parcourait ses catégories une à une, et la parente d'une sous-catégorie trouvait son enfant encore debout et refusait. **Tout compte ayant créé une sous-catégorie devenait indestructible** — et créer une sous-catégorie est une action ordinaire de cet écran. Le hook de requête ne se déclenche que pour une suppression demandée, seul cas qui concerne ce garde-fou.
- **Ce défaut avait échappé à ma propre mesure d'attribution.** J'avais vérifié un utilisateur vide (204) et un utilisateur avec transactions (400, défaut préexistant de `transactions.account`), et conclu que le garde-fou n'aggravait rien. Le cas des sous-catégories n'avait pas été essayé. Une attribution partielle vaut une supposition : le parcours `lets an owner close an account that has a sub-category` existe pour que la conclusion ne repose plus sur ce que j'ai pensé à tester.
- **`category_usage` est une view collection**, comme `account_balances` et `budget_spending` : savoir ce qui retient une catégorie se demande à SQLite, jamais en tirant l'historique dans le navigateur. Ses colonnes portent un `CAST(... AS INT)`, sans quoi l'agrégat revient en valeur JSON.
- **Le bouton « Supprimer » n'apparaît que si la ligne de compteurs de cette catégorie a été lue et vaut zéro** — la ligne, pas seulement la requête : `['categories']` et `['category-usage']` sont deux requêtes qui résolvent dans un ordre quelconque, et une catégorie présente dans l'une et pas encore dans l'autre serait sinon proposée à la suppression sur la foi d'un chiffre que personne n'a lu. **Toute écriture qui touche une transaction, une scission ou une enveloppe invalide `['category-usage']`** : sans cela, une dépense saisie sur un autre écran laissait le bouton en place et le clic partait en 400. Ni cette course ni la précédente n'ont de test — la fenêtre est un aller-retour réseau, qu'aucune assertion ne peut fixer sans temporisation artificielle. — même politique que les chiffres du tableau de bord. Offrir un bouton qui échouera ferait découvrir l'obstacle après l'action ; la ligne dit ce qui retient la catégorie, et la désactivation reste offerte.
- Le module des catégories est passé à `useDerivedMutation` : il était le dernier à invalider en `onSuccess` sans `cancelQueries`, exactement le défaut que `frontend/src/lib/mutations.ts` documente.
- `account_balances` est une view collection, qui somme désormais les transactions.
- Les mutations de comptes invalident aussi `['account-balances']` : le solde est dérivé côté serveur et aucun canal realtime ne le pousse.

### Corriger une ligne après sa création (PR 6/7)

- **Un formulaire par objet, partagé entre créer et corriger** (`category-form.tsx`, `account-form.tsx`), comme `QuickEntryForm` l'est depuis l'étape 4. Une seconde copie serait un second endroit où les règles sur un nom, une nature ou un ornement peuvent diverger — et elles divergent toujours.
- **Les grilles d'apparence n'ouvrent pas pareil des deux côtés, et c'est voulu.** À la création rien n'est coché : une teinte présélectionnée est une réponse que personne n'a donnée, et elle peignait toutes les catégories pareil. À la correction elles ouvrent sur ce que la ligne **porte** — dérivé du nom quand rien n'a jamais été stocké. Une grille vide à côté d'une ligne visiblement colorée se lit comme un défaut, et elle en cachait un vrai : la teinte venant du nom, **corriger l'orthographe repeignait la ligne au passage**. Enregistrer une correction fige donc la teinte dérivée, ce qui est exactement le but.
- **`parentsFor` garde le parent désactivé de l'enfant qu'on corrige.** `selectableParents` écarte les racines désactivées — juste pour la création, silencieusement destructeur pour la correction : le parent tenu par le formulaire ne correspondait plus à aucune option, donc enregistrer **n'importe quoi** remontait la sous-catégorie à la racine. Même principe que la correction d'une transaction, qui garde son compte archivé sur la liste.
- **Deux niveaux, et c'est l'écran qui les tient, pas le schéma.** Le formulaire de correction n'offre aucun parent à une catégorie qui a déjà des enfants : la liste dessine les racines puis les enfants de chacune, donc un troisième niveau ne serait tout simplement pas dessiné. `categories.parent` accepterait pourtant l'écriture ; consigné au §8.
- **Le renommage ne rejoue rien**, et c'est un parcours qui le dit, pas une lecture du schéma : une transaction pointe sur sa catégorie par relation, donc l'historique lit le nouveau nom immédiatement. La **fusion** de `CAT-02`, elle, déplace des lignes ; elle reste au §8.
- **Le solde initial est modifiable, le compte archivé ne l'est pas.** Le premier parce qu'il n'y a aucun retour en arrière autrement — un compte s'archive et ne se supprime pas, donc la seule issue était de porter le mauvais total pour toujours ; rien n'est réécrit, tous les soldes sont sommés à la lecture. Le second parce qu'un compte hors d'usage n'a qu'une chose à faire : être restauré, et un bouton de plus est un bouton devant celui-là.
- **`SECONDARY_BUTTON_CLASS` est une constante, pas un composant**, comme `CONTROL_CLASS` à côté : deux de ses dix-sept emplacements sont des liens et non des boutons. Elle était écrite treize fois à la main et avait déjà divergé — `rounded-md` dans chaque ligne de liste, `rounded-full` sur la feuille qui s'ouvre par-dessus, donc appuyer sur « Modifier » changeait la forme du bouton sous le pouce. Les appelants n'ajoutent que ce qui leur est propre.
- **`ListSkeleton` avait 20 px de coins et les listes qu'il remplaçait 6.** Les jetons `--radius-field` et `--radius-card` avaient été donnés aux composants partagés et jamais aux écrans : la page changeait de forme au moment où les lignes arrivaient. `auth-layout` et l'écran du compte gardent l'ancienne forme — ils sont le sujet de la PR 7/7.
- **Les deux lignes ont été remesurées à 390 px, et la mesure a corrigé un commentaire que j'avais écrit sans elle.** J'avais noté que trois boutons ne tenaient pas sur une ligne : ils tiennent — 86 + 102 + 102 et deux écarts, soit 306 px de boutons dans les 332 qu'offre la ligne, et le nom « Abonnements et services » n'est pas tronqué. Côté comptes, 138 px de solde et 180 de boutons dans 332, une ligne avec 14 de marge. `flex-wrap` reste, mais comme la marge de ces 26 px et non comme une nécessité. **Cinquième fois que ce dépôt mesure une ligne de liste qui gagne quelque chose à gauche ou à droite** ; la mesure se prend dans un parcours jetable, il n'en reste rien au dépôt.
- **`useEntryStreak` rendait `undefined` sur une série absente**, ce que TanStack Query refuse (« Query data cannot be undefined ») : depuis la PR 5/7, chaque écran montant le tableau de bord journalisait cette erreur, invisible à l'utilisateur mais assez bruyante pour cacher une vraie dans la sortie des parcours. Rend `null`.

## Transactions, virements et scissions

- **Montants toujours positifs** ; `type` porte le sens. Une colonne signée laisserait une « dépense » de -5000 signifier un revenu, et chaque agrégat devrait s'en prémunir.
- Un virement s'écrit en **deux lignes** de types `virement_sortant` et `virement_entrant`, reliées par `transfer_group`. Écart assumé au schéma des specs, qui prévoyait un unique `virement` : la view a besoin du sens pour choisir le signe, et deux valeurs explicites évitent un second champ conditionnel.
- Une transaction scindée est **plusieurs lignes ordinaires** partageant `split_group`. Chacune compte une fois partout — soldes, budgets, rapports — donc une seule règle d'agrégat, pas deux opposées.
- **La paire d'un virement se tient après l'écriture, pas seulement pendant.** La route ne garantissait l'atomicité qu'à la création : supprimer une seule jambe faisait passer le total des soldes de 170 000 à 200 000, par le bouton « Supprimer » ordinaire. `pb_hooks/keep_transfer_pairs.pb.js` fait tomber les deux ensemble — la boucle ne se referme pas parce que le partenaire n'est cherché qu'**après** `e.next()`, donc la seconde jambe ne trouve plus rien. Et la `updateRule` exclut désormais toute ligne portant un `transfer_group` : une jambe ne se modifie pas seule, un `PATCH` du `type` inventait 60 000 F.
- **Une seule écriture TypeScript de la règle « quels types créditent un solde »** : `isCredit()` dans `collections.ts`, utilisée pour le signe _et_ pour la couleur. La copie SQL dans la view `account_balances` est irréductible — SQLite ne peut pas l'appeler — donc tout changement se porte aux deux endroits, et nulle part ailleurs.
- **Virements et scissions passent par une route serveur** (`pb_hooks/transfers.pb.js`, `splits.pb.js`) qui écrit dans une seule transaction SQLite. Deux écritures client laisseraient un débit sans crédit sur une coupure. Ne pas contourner ces routes depuis le frontend.
- **Une transaction se corrige pendant 30 jours après sa saisie, puis c'est de l'historique** (`TRX-05`, `pb_hooks/limit_entry_changes.pb.js`). Le délai court depuis `created`, **jamais depuis `date`** : une dépense antidatée au mois dernier mais saisie ce matin est une erreur fraîche. `created` porte `onUpdate: false`, donc un `PATCH` ne peut pas déplacer l'échéance qu'on lui oppose. **La suppression suit la même fenêtre** : laissée ouverte, elle défaisait la règle en deux clics — supprimer la ligne ancienne, la ressaisir au chiffre voulu.
- **Les deux handlers de cette fenêtre sont les variantes `…Request`, et ce n'est pas une question de style.** `keep_transfer_pairs.pb.js` supprime la jambe jumelle par `e.app.delete()`, une suppression interne qu'un hook de modèle refuserait — laissant une demi-paire debout. Et `users` cascade vers `transactions` : sur `onRecordDelete`, **fermer un compte devenait impossible dès qu'une écriture avait plus d'un mois** (`USR-04`), soit pour tout le monde le jour où quelqu'un s'en sert. Mesuré le 30/08/2026 en substituant le hook de modèle : `HTTP 400 … within 30 days` sur le `DELETE` de l'utilisateur. Troisième hook à rencontrer cette cascade après `guard_category_deletion` et la fermeture de compte elle-même ; le parcours `lets an owner close an account whose entries are older than the edit window` existe pour qu'il n'y ait pas de quatrième fois non attrapée.
- **Modifier et supprimer ne sont pas la même permission, et les confondre coûte de l'argent.** Une jambe de virement **se supprime** — la paire tombe ensemble, c'est la conception — mais ne **se modifie** jamais seule : un `PATCH` de son `type` avait inventé 60 000 F. `transactions-page.tsx` porte donc deux prédicats, `stillRemovable` et `stillCorrectable`, pas un. Conditionner les deux boutons sur la règle unique a fait disparaître le bouton « Supprimer » des virements, et c'est un parcours vert depuis deux étapes qui l'a dit — pas une relecture.
- **La règle de la fenêtre est écrite une seule fois** (`packages/domain/src/entry-window.ts`), et les deux bornes sont des paramètres plutôt qu'un appel à l'horloge : c'est ce qui la rend testable sans faux timer — le dépôt n'en utilise nulle part — et ce qui garantit que le bouton à l'écran et le refus du serveur ne peuvent pas diverger. **`created` arrive au format `2026-08-30 12:00:00.000Z`, avec une espace et non le `T` d'ISO-8601** : goja ne le parse pas, d'où la normalisation dans le module. Un horodatage illisible **ferme** la fenêtre, jamais l'inverse — laisser passer une modification est le seul résultat qu'on ne peut pas reprendre.
- **Antidater est le seul moyen de tester cette fenêtre** : le hook lit l'horloge réelle. `frontend/test/pb_hooks/backdate_probe.pb.js` écrit `created` directement en SQLite — le champ est `autodate`, donc l'API le refuse, et passer par l'API des enregistrements déclencherait le garde qu'on veut mesurer.
- `pb_hooks/guard_owned_relations.pb.js` vérifie la propriété des relations **à la création comme à la mise à jour**, pour `transactions` _et_ `budgets` : PocketBase n'applique `account.user = @request.auth.id` qu'à la création. Le trou a été mesuré deux fois — un `PATCH` déplaçait une transaction sur le compte d'un tiers (étape 4), puis une enveloppe sur la catégorie d'un tiers (étape 5). **Toute nouvelle collection portant une relation vers un autre enregistrement du propriétaire passe par ce fichier.**
- Un formulaire dont un `<select>` démarre sur une valeur sans option correspondante **ne peut pas être soumis** : le navigateur affiche la première option sans émettre d'événement, et la valeur du formulaire reste vide. Les formulaires ne sont montés qu'une fois leurs options connues. Un parcours qui appelle toujours `selectOptions()` ne verra jamais ce défaut.
- Les routes convertissent toute entrée invalide en 400, y compris les identifiants inconnus : un `findRecordById` non encadré répondait 404 sur un POST, ce qui se lit « cette route n'existe pas ». Le message ne distingue pas l'inconnu de l'étranger, sans quoi il dirait si un identifiant existe.
- **La suppression d'un compte utilisateur échoue déjà** (HTTP 400, `Failed to delete record`), indépendamment des virements : `transactions.account` est une relation non cascadante et retient le compte. Mesuré au 19/08/2026 ; à traiter avec USR-04 à l'étape 8.
- `created` et `updated` ne sont plus implicites depuis PocketBase 0.23 : toute collection qui doit être triée par ordre d'insertion doit les déclarer explicitement.

## Le montant se saisit au pavé (`TRX-09`)

- **`inputMode="none"`, jamais `readOnly`.** C'est la différence entre remplacer le clavier du système et supprimer la saisie : le champ reste un `<input>` ordinaire, donc le clavier physique et les technologies d'assistance y écrivent toujours. Les touches sont des `<button>` pour la même raison — atteignables à la tabulation et à la navigation d'un lecteur d'écran. C'est le « jamais la seule voie » de l'exigence, et il se perd au premier `readOnly`.
- **Le champ ne nettoie pas ce qu'on tape, il le laisse passer.** Ma première version retirait tout ce qui n'était pas un chiffre : `1500,75` perdait sa virgule et devenait **150 075 F**, en silence, dans le champ qui décide d'une dépense. Une erreur d'un facteur cent. Deux parcours qui existaient depuis l'étape 4 (`refuses the amount "-500"`, `"1500,75"`) l'ont attrapée. Le franc n'a pas de subdivision, donc il n'y a pas de bon montant à deviner : `tidy` ne range que ce qui est déjà entièrement chiffré, et le reste part au schéma qui le refuse.
- **La valeur portée est en chiffres nus, le montant groupé vit dans la ligne d'état.** Grouper dans le champ mettrait un séparateur entre le curseur et le chiffre derrière lui, là où la touche « retour arrière » semble ne rien faire.
- **La ligne d'état (`role="status"`) est la seule chose qui dit le montant en cours.** Appuyer sur une touche déplace le focus sur la touche : un lecteur d'écran annonce « 2 » et rien du total. Sabotage vérifié — lui retirer son rôle rougit deux parcours.
- **Le pavé ne se replie pas au focus, et le replier aurait bel et bien acheté de la place.** 218 px sur les 806 que tient la feuille contre une fenêtre de 760 : un pavé qui se ferme quand la catégorie prend le focus supprimait tout le défilement. Deux choses coûtent plus cher que ce défilement. **La première** : il faudrait le rouvrir en focalisant le champ, et rien ne le focalise — **`showModal()` donne le focus au bouton « Fermer »**, et React ne rend pas d'attribut `autofocus` que le `<dialog>` préférerait, de sorte que l'`autoFocus` du champ « Montant » n'avait jamais rien fait depuis l'étape 4. Le montant attendrait donc derrière une tape sur un contrôle qui ressemble à un champ ordinaire. **La seconde** : il se replierait pendant que le sélecteur natif de catégorie est ouvert — une surcouche système qui masque la page bougeant de 218 px dessous. Un saut sous le pouce coûte une fausse tape ; un défilement est un geste qu'on a choisi de faire. _La première version de cette entrée affirmait que replier n'achetait aucune place. C'était faux, et calculable depuis mes propres mesures — trouvé en revue._
- **La feuille de saisie défile désormais, mesuré à 390×844.** Avant le pavé : 542 px de contenu, rien à faire défiler. Après : 806 px dans 760 (la feuille est passée de 85 à 90 dvh, les touches de 56 à 48 px), soit 46 px de défilement, et le bouton « Enregistrer » dont le haut affleure le bord. C'est une régression assumée sur l'objectif des dix secondes ; la ramener à zéro demandait de replier le compte, ce qui coûterait à quiconque a un compte bancaire **et** du mobile money — la norme ici.
- **Le champ ne prend pas de `ref`.** La règle du compilateur React contre la lecture d'une ref pendant le rendu refuse la ref-fonction de react-hook-form, et signale au passage le `value` et le `onChange` posés à côté. Conséquence : le formulaire ne déplace plus le focus vers le montant refusé — le message porte son `role="alert"`.
- **La borne de douze chiffres tient les touches, et rien d'autre.** Elle s'appliquait d'abord aussi à la frappe : `1234567890123` devenait `123456789012`, enregistré, un facteur dix perdu en silence — **la classe d'erreur exacte que la virgule avait fait corriger trois lignes plus haut, dans la même PR**. Trouvé en revue. Les deux justifications avancées pour cette borne étaient fausses : un `<input>` ne grandit pas, il fait défiler son texte (mesuré à vingt chiffres — champ 284 px inchangé, contenu 324, feuille et page à 390), et `toMoney` refuse déjà tout ce qui sort des entiers exacts. Sur le pavé la borne est un arrêt visible — la touche ne fait rien, aucun chiffre n'apparaît ; sur la frappe c'était une réécriture muette.
- **Le pavé ajoute, il ne remplace jamais** : sur la feuille de correction, où le champ arrive prérempli, changer 20 000 en 25 000 coûte cinq ⌫. Le clavier du système donnait « tout sélectionner », que `inputmode="none"` retire ; l'appui long garde les poignées de sélection, donc ce n'est pas une impasse. Dette produit assumée, consignée au §8 avec le coût de chacune des trois issues envisagées.
- Les autres champs monétaires — plafond, dette, mensualité, remboursement, solde initial — gardent le clavier du système. Écart assumé, consigné au §8 des specs fonctionnelles avec ce qu'une spécification devra trancher.

## Budgets, seuils et reports

- **Une enveloppe par catégorie et par mois**, `month` en texte `YYYY-MM`, avec un index unique `(user, month, category)` : une seconde enveloppe couperait le plafond en deux et tous les totaux mentiraient.
- **`carried_amount` vit à côté de `cap_amount`, jamais dedans.** L'utilisateur doit continuer à voir le plafond qu'il a choisi, et une valeur absolue rend le report rejouable sans se cumuler.
- Le report a **deux moments**, pas un : le cron du 1er couvre les enveloppes déjà là, et `onRecordAfterCreateSuccess(budgets)` couvre les autres. Sans ce second chemin, un mois dupliqué le 3 ne recevrait jamais le report appliqué le 1er. Les deux appellent `pb_hooks/jobs/carry_over.js` — un module requis par les handlers, pas un hook : PocketBase ne charge que les `*.pb.js`.
- **L'alerte est une réconciliation, pas une réaction.** `pb_hooks/jobs/budget_alerts.js` ne demande jamais « que vient-il de se passer » mais « quels seuils cette enveloppe atteint-elle maintenant » : il crée ce qui manque et retire les alertes non lues qui ne se justifient plus. Branché sur la création, la mise à jour **et** la suppression, d'une transaction **comme d'une enveloppe** — la seule création laissait une dépense corrigée à la hausse sans alerte, et laissait pour toujours l'alerte d'une dépense supprimée, la déduplication interdisant de la reproduire. Une alerte déjà écartée par l'utilisateur reste : c'est de l'historique.
- **L'enveloppe est l'autre moitié de la question, et pendant six étapes seul le côté dépense la posait.** Poser un plafond sur une catégorie **déjà dépensée** — la façon ordinaire de découvrir qu'on dépense trop — n'annonçait rien jusqu'à la dépense suivante ; relever un plafond en réponse à une alerte gardait l'alerte. Trouvé en regardant l'écran, pas en lisant le code : sur des données semées, le panneau disait « Aucune alerte » à côté d'une enveloppe visiblement dépassée. Aucun test ne pouvait le voir — les douze scénarios d'alerte partaient tous d'une enveloppe déjà en place. **Supprimer l'enveloppe retire ses alertes non lues** : `reachedThresholds` rend `[]` pour un plafond nul, donc la réconciliation existante suffisait, il ne lui manquait que d'être appelée.
- Une notification porte un **`subject` textuel indexé** (`YYYY-MM@categoryId`). Dédupliquer sur le `payload` obligeait à relire toutes les notifications de l'utilisateur à chaque saisie, un filtre sur un chemin JSON ne ramenant rien.
- **`carried_amount` est écrit par le serveur, dans `onRecordCreate`, après avoir été remis à zéro.** Il était réglable par le client : un plafond de 1 franc avec un report de 5 000 000 était accepté tel quel, et l'enveloppe ne déclenchait plus jamais de seuil.
- **Le « reste à vivre » ne suit pas la formule des specs à la lettre.** « Revenus − charges fixes − échéances − dépenses réalisées » compte deux fois une charge fixe déjà payée. Seule la part **non encore payée** des enveloppes fixes est déduite, sinon payer son loyer ferait baisser le reste à vivre deux fois. **Les échéances de dettes suivent exactement la même règle** (`unpaidInstalment`) : la mensualité moins ce qui a déjà été remboursé ce mois-ci, plafonnée à ce qui reste dû, et rien pour l'argent qu'on doit à l'utilisateur. Le terme est resté à zéro entre les étapes 5 et 7 — un commentaire annonçait qu'il rejoindrait le calcul au tableau de bord, où il n'a rejoint personne, et une mensualité de 90 000 F CFA était affichée comme disponible.
- **PocketBase ne sait pas typer un agrégat dans une view** : un `SUM()` non casté revient comme valeur JSON et `getInt()` y lit 0 — mesuré, le hook d'alerte ne se déclenchait jamais. Toute colonne calculée d'une view porte un `CAST(... AS INT)`.
- **Un champ `json` relu depuis un enregistrement n'est pas un objet JS** : `payload.month` y vaut `undefined`, et un filtre sur un chemin JSON (`payload.month = {:month}`) ne ramène rien. Passer par `JSON.parse(String(...))` et comparer en JavaScript.
- **Une erreur levée dans `onRecordAfterCreateSuccess` revient au client en HTTP 400 sur l'enregistrement lui-même** — mesuré. Tout hook accessoire (alerte, report) enveloppe donc son corps dans un `try/catch` qui journalise : une notification impossible ne doit jamais coûter à l'utilisateur la saisie qu'il vient de faire.

## Dettes et échéanciers

- **La mensualité est une donnée, pas un résultat** (`DET-01`) : l'utilisateur dit ce qu'il paie chaque mois, donc le nombre d'échéances tombe des termes, et la dernière est la petite — jamais la grosse. Réclamer plus que ce qui reste dû prendrait un argent que l'emprunteur ne doit pas.
- **La propriété tenue par les tests n'est pas le détail des échéances mais leur somme** : les parts de capital rendent exactement ce qui a été emprunté, quel que soit l'arrondi mensuel, y compris sur une centaine d'échéances.
- **Un taux n'est pas un montant.** `interest_rate` est le seul nombre décimal du schéma : 7,5 % est banal. Chaque franc qu'il produit est arrondi à l'entier immédiatement.
- **`debts.remaining_amount` est stocké, contre la règle du projet sur les cumuls dérivés.** L'exception est bornée et tient à une condition : ce champ n'est **jamais ajusté**, il est **rejoué** depuis l'historique complet des remboursements à chaque écriture (`pb_hooks/jobs/debt_balance.js`). Décrémenter puis ré-incrémenter serait le choix évident et le mauvais : corriger un remboursement ancien change ce que tous les suivants ont remboursé, leurs intérêts ayant été calculés sur un capital qui vient de bouger. Vérifié discriminant : remplacer le rejeu par un cumul rend le test de suppression rouge.
- Les hooks de remboursement tournent **dans** l'écriture (`onRecordCreate`, pas `AfterCreateSuccess`) : un rejeu qui échoue doit emporter l'écriture, et la ventilation appartient à la réponse rendue au client.
- **Le rejeu est autoritaire, jamais défensif.** Le hook de mise à jour d'une dette laisse l'écriture passer puis réécrit `remaining_amount` et `status` depuis l'historique. Rétablir la valeur d'avant, au lieu de recalculer, défait l'écriture du rejeu lui-même et boucle à l'infini — mesuré.
- **Le rejeu s'arrête quand la dette a disparu.** Supprimer une dette cascade vers ses remboursements, dont chacun déclenche un rejeu : recharger la dette y levait, et une dette portant le moindre remboursement devenait indestructible.
- **Le rejeu relit chaque remboursement avant de le comparer.** L'enregistrer déclenche le hook qui rejoue tout ; sans relecture, la boucle appelante comparait des copies antérieures à ce rejeu imbriqué et les réenregistrait toutes. Mesuré à 24 échéances : 249 ms contre 68 ms après correction ; à 50 : 1098 ms contre 214 ms. Non couvert par un test — une assertion de temps ne peut pas être à la fois stable en CI et discriminante ici.
- Les rappels d'échéance sont clés par `(date, dette, décalage)` dans le `subject` : c'est ce qui rend le cron quotidien rejouable après une panne sans sonner deux fois.
- Un rappel ne précède jamais la première échéance de l'échéancier affiché : les deux lectures du même calendrier se contredisaient pour une dette ouverte le jour même.
- **Les notifications d'échéance n'ont pas encore d'écran.** Le cron les produit, le panneau des budgets ne montre que les dépassements. Le centre de notifications est prévu à l'étape 7.

## Coque et navigation

- **Neuf destinations, cinq dans la barre.** Accueil, Transactions, Budgets, Dettes et Comptes sont ce pour quoi on ouvre l'application ; Catégories, Épargne, Rapports et Mon compte sont derrière un bouton « Menu ». Une barre qui tient tout ne tient rien, et cinq est là où un pouce cesse de distinguer.
- **Une seule navigation dans le DOM à la fois, choisie par `matchMedia` et non par `md:hidden`.** Deux navigations masquées l'une l'autre, c'est deux repères `<nav>` et deux liens « Comptes » : `display: none` les sort de l'arbre d'accessibilité mais pas du document, et **les parcours lisent le document — ils montent le routeur sans feuille de style**. Une barre dupliquée aurait rendu `getByRole('link', { name: 'Comptes' })` ambigu dans huit fichiers existants. D'où `frontend/src/lib/media-query.ts`.
- **Le rail remplace la barre _et_ le menu à partir de 768 px.** La propriété qui compte n'est pas qu'un rail apparaisse mais que les deux autres disparaissent : une barre fixée en bas d'une fenêtre de bureau est un téléphone étiré, et un bouton « Menu » à côté d'une navigation qui montre déjà tout est un bouton qui ouvre ce qui est ouvert.
- **L'identité est toujours à côté du bouton de déconnexion** — dans le menu sur téléphone, au pied du rail sur écran large. C'est l'invariant, et il n'a pas bougé : appuyer sur ce bouton ne doit jamais être un pari sur les données que l'on quitte. **Ce qui a bougé, et le coût est réel** : sur téléphone, un coup d'œil ne dit plus quel compte est connecté, il faut ouvrir le menu. Accepté parce que l'en-tête n'en disait déjà rien d'utile — l'adresse y était coupée à « Bon retour, capture17882…@… » sur 390 px, et une adresse tronquée n'identifie personne.
- **L'adresse s'enroule, elle ne se tronque pas.** Mesuré : dans la feuille comme au pied du rail, `truncate` rendait encore « capture17883… ». Les deux endroits ont de la hauteur à revendre ; la couper n'achetait rien.
- **Le menu se ferme sur le clic, et c'est tout le mécanisme.** Naviguer ne demande aucune aide : **chaque écran rend son propre `AppShell`**, donc un changement de route démonte `ShellMenu` et `open` renaît à `false`. La première version surveillait `useLocation` avec un `lastSeenPath` — du **code mort** : la condition ne pouvait jamais être vraie, l'état qu'elle protégeait ayant déjà disparu avec le démontage. Trouvé en sabotant, pas en relisant : retirer cette moitié laissait dix parcours sur dix verts.
- **Le cas que la moitié « location » prétendait couvrir est celui qu'elle ratait.** Toucher la destination où l'on est déjà ne change pas le `pathname` : le menu restait ouvert, c'est-à-dire un `<dialog>` modal — piège à focus, fond inerte — par-dessus la page qu'on venait de demander, et rien à l'écran n'ayant bougé, aucune raison de chercher « Fermer ». Le commentaire d'origine citait précisément ce cas comme la raison de préférer la location au clic. **Si la coque montait un jour dans une route de mise en page, le démontage cesserait d'opérer** ; le parcours du bouton « précédent » est ce qui le dirait.
- **`useMediaQuery` mémoïse son `subscribe`.** `useSyncExternalStore` le rejoue dès que son identité change, donc une fermeture en ligne démonte et remonte l'écouteur `matchMedia` à chaque rendu. Mesuré : **4 abonnements / 3 retraits** avant, **2 / 1** après, pour un montage et une navigation. `useAuth` garde ses deux rappels au niveau du module pour la même raison ; celui-ci prend un paramètre, donc il mémoïse.
- **Le redimensionnement se teste sur le hook, jamais à travers l'application.** Un premier test redimensionnait la fenêtre avec l'application entière montée et regardait le rail apparaître : **retirer complètement l'abonnement le laissait vert**. Mesuré — le redimensionnement ne remonte pas l'application, mais il fait rafraîchir une requête, le composant de route se re-rend, la coque avec lui, et `useSyncExternalStore` relit l'instantané en chemin. La largeur était bonne pour une raison étrangère à l'abonnement, qui est pourtant la seule chose que ce hook ajoute à une lecture unique. `media-query.journey.tsx` monte une sonde que rien d'autre ne re-rend.
- **Épargne et Rapports ont leur entrée et leur écran d'attente avant d'avoir leur fonctionnalité** (§8 des specs fonctionnelles). Une entrée qui n'apparaît qu'à la livraison laisse conclure que le produit ne fait pas d'épargne, et l'adresse répond « Page introuvable », ce qui se lit comme un lien cassé et non comme un chantier. Un écran d'attente **dit ce qui est prévu et renvoie à ce qui répond déjà** — « Bientôt » tout seul coûte une tape et ne rend rien.
- **Les parcours tournent en 414×896**, un téléphone : c'est la branche mobile qui rend par défaut, et le rail ne se teste qu'en posant explicitement `page.viewport(1280, 900)`.
- **`import { page } from 'vitest/browser'`, jamais `@vitest/browser/context`.** Le second est déprécié depuis Vitest 4 **et n'expédie pas ses types** en 4.1.10 — son `exports` pointe sur un `context.d.ts` absent du paquet, ce qui casse `typecheck` et `lint` sans casser les tests. Vérifié dans la doc, pas de mémoire.

## Tableau de bord et PWA

- **La répartition est un anneau doublé d'une légende ordonnée, et c'est la légende qui porte la lecture** (`RAP-02`). L'objection au camembert tient toujours — comparer des angles est la comparaison la plus difficile qui soit — et c'est elle qui décide de la répartition des rôles : les chiffres et les parts sont écrits dans la légende, du plus grand au plus petit, et **l'anneau est `aria-hidden`** parce qu'il ne dit rien que la liste ne dise. Ce qu'il ajoute est le lien avec le reste de l'application : un arc porte la teinte que sa catégorie porte partout ailleurs (`CAT-04`). Aucune dépendance de graphiques : un `<circle>` de circonférence 100, où une longueur de tiret **est** un pourcentage. _La version précédente de cette entrée disait « une liste de barres, pas un camembert » ; les specs remises d'aplomb à la PR 1/7 demandaient déjà l'anneau, et la note était restée en arrière._ Les courbes sur douze mois de `RAP-02` restent hors périmètre : c'est là qu'une librairie gagnera sa place.
- **La tranche d'agrégat s'appelle « Autres catégories », jamais « Autres ».** Une des catégories semées à l'inscription s'appelle littéralement « Autre », et les deux se sont retrouvées dans la même liste sans que rien ne les distingue. Trouvé par un parcours existant, pas en relisant. Au-delà des cinq premières, le reste est une tranche et non un oubli : un anneau qui montrerait cinq catégories sur huit prétendrait dire où part l'argent en en cachant une partie.
- **Une seule liste de clés pour toute écriture de transaction** (`TRANSACTION_KEYS`, `transactions-api.ts`). Les trois modules qui écrivent des transactions — saisie, scissions, virements — tenaient chacun la leur, et elles avaient divergé. **Mesuré** : une dépense de 20 000 F saisie depuis le tableau de bord déplaçait le solde et rien d'autre — « Dépenses du mois » restait à `0 F CFA`, « Reste à vivre » à `0 F CFA`, et la série à « aucune », pendant que l'écriture était en base. Tout est dérivé côté serveur et aucun canal realtime ne le pousse. Défaut préexistant sur deux chiffres, trouvé en revue seulement parce que la série en ajoutait un troisième. Les virements ne touchent ni les totaux du mois ni les enveloppes (`CPT-05`), donc deux clés y sont inutiles : une relecture d'une ligne coûte moins qu'une seconde liste à tenir en accord.
- **La répartition attend les noms, pas seulement les montants.** Sans les catégories, chaque ligne retombe sur « Sans catégorie » et chaque arc sur l'unique teinte que cette chaîne dérive : cinq catégories se dessinent en une ligne grise répétée et l'anneau en une couleur unie. Ce n'est pas une image incomplète mais une image fausse, et c'est l'anneau qui a rendu bruyante une brèche que les barres rendaient discrète. `ready` exige donc les **deux** requêtes.
- **Une course entre deux requêtes réelles se teste en faisant échouer l'une d'elles**, jamais en la ralentissant : `frontend/test/pb_hooks/blind_categories_probe.pb.js` refuse la liste des catégories aux comptes dont l'adresse commence par `blindcat`, sauf pour les requêtes portant l'en-tête de semis. Une temporisation ne serait ni stable ni discriminante.
- **Un piège déjà consigné, rencontré une seconde fois** : ce parcours attendait `getByRole('heading', { name: 'Solde total' })` avant d'affirmer une absence. Les titres sont du texte statique, présents avant la moindre requête — le test passait donc dans les deux sens. **Une assertion d'absence attend une valeur, jamais un libellé**, comme `dashboard-load.journey.tsx` le dit déjà pour la performance.
- **L'arithmétique de dates ne repasse jamais par UTC.** `dayBefore` construisait une `Date` à midi local, reculait d'un jour et relisait par `toISOString()`. Mesuré sous node avec `TZ` : juste à UTC, Abidjan, Auckland et São Paulo, **faux d'un jour au-delà d'UTC+12** — `dayBefore('2026-09-05')` rendait `2026-09-03` à Kiritimati, et une série debout s'y lisait « aucune série ». La version retenue calcule sur la chaîne et ne convertit jamais ; la bascule de mois demande encore à une `Date` la longueur de février, mais la construit et la relit avec des accesseurs locaux. **Le semis du parcours portait le même idiome**, donc le défaut ne pouvait pas venir de là — les deux se trompaient ensemble. Non couvert par un test : la suite tourne un seul navigateur dont elle ne peut pas faire varier le fuseau par test, et un assistant qui redériverait le jour attendu ne ferait que réécrire l'implémentation.
- **La série de saisie est comptée par SQLite, pas par le navigateur** (`RAP-06`, view `entry_streaks`, îlots de jours consécutifs). Le tableau de bord ne charge **aucune** transaction : compter côté client aurait voulu dire rapatrier toutes les dates de l'historique à chaque ouverture, c'est-à-dire faire rougir `dashboard-load.journey.tsx`, dont c'est la raison d'être. Coût mesuré : **80 ms contre 74** sur 5 000 entrées.
- **La view dit la longueur de la série et le jour où elle s'arrête ; elle ne dit jamais si ce jour est aujourd'hui.** Une view ne prend pas de paramètre, donc sa seule horloge serait `date('now')`, qui est UTC — et ce dépôt tient que le jour appartient au fuseau de l'utilisateur (`todayLocally`). La moitié sensible au fuseau reste donc au client, la moitié coûteuse reste en SQL.
- **Une série qui s'est arrêtée hier tient encore.** À huit heures du matin personne n'a rien saisi, et répondre « aucune série » punirait d'avoir ouvert l'application tôt. L'écran doit le coup de pouce à la place : la série est debout, et c'est aujourd'hui qui la garde.
- **Le conseil ne répète jamais le montant imprimé au-dessus de lui** (`RAP-07`). Une première version ouvrait sur « Il reste X », à deux centimètres du même X en trois fois la taille ; un parcours existant l'a dit en trouvant ce chiffre deux fois. Ce que le conseil ajoute est le passage au par-jour — un reste mensuel n'est pas un chiffre sur lequel on agit, ce qui reste par jour l'est. La division arrondit **vers le bas** : arrondir vers le haut distribuerait une allocation que le mois ne peut pas payer.
- **Les deux chiffres secondaires restent pleine largeur, et c'est une mesure.** Deux demi-cartes ont été essayées : « 12 645 000 F CFA » demande **172 px** là où une demi-carte à 390 px en offre **147**, et il débordait dans sa voisine. Le franc n'a pas de petits montants — un solde de ménage fait sept chiffres en ordinaire — et réduire la police jusqu'à ce que ça rentre laisserait un chiffre de la taille du texte courant. La hiérarchie est portée par la bordure et le corps 3xl de la carte principale.
- **Une assertion sur l'anneau ne passe jamais par `querySelector('svg')`.** Le premier `<svg>` du document est une icône lucide de la navigation, que lucide marque déjà `aria-hidden` : le test passait avec l'anneau entièrement exposé. Mesuré en retirant l'attribut. On l'atteint par un de ses arcs (`[data-hue]`), puis `closest('svg')`.
- **Le bouton d'une alerte est une coche, et son nom accessible porte le libellé.** « Marquer comme lue » prenait près de la moitié de la ligne à 390 px et pliait chaque alerte sur trois lignes.
- **Les figures du mois vivent dans `frontend/src/budgets/month-figures.ts`**, partagées par l'écran des budgets et le tableau de bord : les deux ne peuvent pas se contredire sur le même mois.
- **Une seule formulation par notification** (`frontend/src/home/notification-centre.tsx`), quel que soit l'écran qui l'affiche.
- **Les icônes de lancement sont dessinées par `frontend/scripts/make-icons.mjs`**, pas déposées en binaire opaque : `pnpm icons:build` les régénère, et la source des pixels est lisible.
- Le service worker est **désactivé pendant les parcours** (`disable: process.env.VITEST === 'true'`) : il servirait le build d'un test au suivant.
- **Aucun chiffre n'est affiché avant d'avoir été lu.** Les trois totaux du tableau de bord valent `—` tant que leurs requêtes n'ont pas abouti, et `budgeted === 0` ne devient « Aucune enveloppe définie » qu'une fois les enveloppes chargées. La première version affichait un `0` assuré pendant le chargement comme après un échec — sur les nombres mêmes qui décident d'une dépense. Le parcours tient la propriété par la négative : jamais de « 0 F CFA » quand la session est refusée.
- **Le solde total ne compte que les comptes ouverts** (`CPT-04`) : un compte archivé ne peut plus ni être débité ni recevoir de virement. Et un solde que le client n'a pas su relire rend le total inconnu, jamais nul — l'absorber en zéro le sous-estimerait en silence.
- **Le service worker n'attrape ni `/api/` ni `/_/`** (`navigateFallbackDenylist`). PocketBase sert la SPA, son API et sa console d'administration sur une seule origine : sans ces exclusions, le premier navigateur ayant ouvert l'application reçoit la coquille précachée à la place de la console. Vérifié dans le `sw.js` généré, pas dans la configuration.
- **Une notification se formule à la lecture, pas à l'écriture.** Le rappel est écrit le matin où le cron passe ; relu deux jours plus tard, il annonçait toujours « dans 3 jours ». Le compte à rebours se recalcule depuis `dueDate` à l'affichage, et `wordingOf` prend un `today` pour que le parcours puisse le fixer.
- **Le rappel le plus proche retire le précédent.** Les trois décalages J-3/J-1/J empilaient trois cartes le jour de l'échéance. Le cron marque comme lus les rappels non lus de décalage supérieur pour la même paire (date, dette) : la carte restante est la seule à jour, les autres restent en historique.
- **`wordingOf` rend `undefined` plutôt qu'un libellé creux**, et le centre écarte alors la ligne : une carte disant « Notification » n'apprend rien et demande quand même à être écartée. C'est aussi ce qui permet aux rappels d'échéance de s'afficher quand les catégories, elles, n'ont pas pu être lues — seules les alertes de budget en dépendent.
- **L'installabilité réelle ne peut pas être vérifiée avant le déploiement** : un service worker exige HTTPS. Ce qui est vérifié ici, c'est que le manifeste, le worker et les icônes sont servis avec les bons types. Le test sur appareil appartient à l'étape 8.

## Performance et accessibilité, mesurées

- **Le tableau de bord répond en 74 ms sur 5 000 entrées réparties sur trois ans**, contre les 2 s que le plan exige (`frontend/src/home/dashboard-load.journey.tsx`). La marge est ce qui dit que l'agrégation est restée dans SQLite ; le jour où un total se calcule côté client, ce test rougit.
- **Une mesure qui n'attend pas les bonnes choses ne mesure rien** : la première version attendait des titres statiques, présents avant la moindre requête, et annonçait 23 ms. Une assertion de performance doit porter sur une valeur, jamais sur un libellé.
- **L'audit WCAG AA est exécuté, pas inspecté** (`axe-core`, sur le tableau de bord et le formulaire de saisie). Vérifié discriminant sur une image sans alternative textuelle. **Vérifié non discriminant sur le contraste** : axe range le contraste en « incomplet » quand il ne peut pas résoudre le fond avec certitude, donc un paragraphe volontairement illisible n'a pas été signalé.
- **Le contraste n'est donc couvert par aucun test.** La palette slate mesurée le 27/08/2026 a été remplacée le 01/09/2026 par les tokens de la refonte ; **les rapports qui font foi sont ceux du §2.1 des specs techniques**, remesurés à cette date. Ne pas citer d'anciens chiffres : ils ont survécu deux jours à la feuille de style qu'ils décrivaient. Une couleur ajoutée ou modifiée se remesure à la main, dans les deux thèmes, la CI ne le fera pas.

## Compte utilisateur : export et fermeture (`USR-04`)

- **Fermer un compte butait sur deux obstacles distincts, pas un.** Le premier était connu depuis le 19/08 : `transactions.account` est **requis et non cascadant**, donc supprimer un propriétaire emportait ses comptes pendant que les écritures y pointaient encore, et PocketBase refusait tout. Le second n'a été trouvé qu'en bisectant l'utilisateur pièce par pièce : **un seul remboursement de dette suffisait à bloquer**, le rejeu réenregistrant une dette dont le propriétaire venait de disparaître — `validation_missing_rel_records` sur un champ que personne n'avait touché. Le premier test échouait sur un scénario contenant les deux ; croire le problème réglé par la migration seule était le piège.
- **Le motif des relations non cascadantes, vérifié à l'exécution** : une relation **optionnelle** est **vidée** à la suppression (`transactions.category` passe à `''`), une **requise bloque**. Seules les requises font obstacle.
- **Cascader `transactions.account` est sûr uniquement parce que `accounts.deleteRule` est `null`.** Un utilisateur ne peut jamais supprimer un compte directement — ils s'archivent — donc la cascade ne part que sur la suppression du propriétaire. Si cette règle changeait, supprimer un compte emporterait son historique.
- **La garde du rejeu est dans le hook de suppression, pas dans `recompute()`** : seules les suppressions paient la relecture du propriétaire, et une cascade est la seule façon pour lui d'être absent.
- **L'export construit l'enregistrement du compte champ par champ**, jamais par sérialisation en bloc. Un export « tout sur moi » est l'endroit le plus facile d'une application pour fuiter un identifiant, et une liste blanche ne peut pas laisser passer un champ ajouté plus tard à la collection. Un parcours vérifie l'absence de `password` et de `tokenKey` dans le document entier.
- **L'identité de l'export vient de la session, jamais d'un paramètre.** La route lit au-delà des règles d'accès par construction — il le faut, pour rassembler sept collections — donc un identifiant fourni par l'appelant livrerait à n'importe qui l'historique financier complet d'autrui. Un parcours le tient.
- **Le tri de l'export se fait sur `id`, pas sur `created`** : ce champ n'est plus implicite depuis PocketBase 0.23 et seules certaines collections le déclarent — trier dessus échoue avec `invalid sort field`. `id` existe partout et rend l'export stable d'une exécution à l'autre.
- **Le bouton de fermeture reste inerte tant que l'adresse n'est pas saisie**, et la comparaison est exacte. Une correspondance approximative annulerait l'intérêt de demander.
- **Le téléchargement de l'export passe par une ancre insérée dans le document, et l'URL objet est révoquée au tick suivant.** Une ancre détachée dont l'URL disparaît dans le même tick que le clic n'enregistre rien du tout sur Safari iOS — la première cible d'une application pensée mobile — pendant que la mutation réussit et que l'écran annonce un fichier que personne n'a reçu.
- **La confirmation de fermeture tolère la casse et les espaces.** PocketBase authentifie sans distinction de casse mais **stocke** celle de l'inscription : une comparaison exacte enfermait quiconque s'était inscrit en `Jean.Dupont@…` hors de sa propre fermeture de compte. Ce qui importe est la délibération, pas l'exactitude du caractère.
- **Le SDK vide lui-même l'authStore** quand on supprime son propre enregistrement (vérifié dans `pocketbase@0.27.1`). Le vider une seconde fois ne ferait qu'émettre un `onChange` de plus. Ce qui tient la redirection est le parcours, qui exige le retour de l'écran de connexion.
- **Le scénario de fermeture porte aussi un virement et une scission.** Ce sont les deux formes de transaction qui traînent leurs propres hooks de suppression, et l'hypothèse d'un troisième blocage y était plausible — `USR-04` en avait déjà connu deux, chacun invisible jusqu'à ce que le scénario l'atteigne. **Mesuré : ils ne bloquent pas.** Le scénario reste, non comme une correction mais comme une garde.
- **Le test de fermeture compte les lignes par une sonde**, pas en interrogeant l'API en tant qu'autre utilisateur : les règles d'accès cachent les lignes d'autrui qu'elles existent ou non, donc cette seconde forme passerait toujours.

## Requêtes et cache

- **Un 4xx n'est jamais réessayé** (`createQueryClient`). Une lecture refusée répond pareil à la dixième tentative : les trois essais par défaut ne faisaient que retarder de sept secondes l'aveu que le chiffre n'a pas pu être lu. Les pannes réseau et serveur gardent leurs essais.
- **L'auto-annulation du SDK PocketBase est désactivée** (`pb.autoCancellation(false)`). Le SDK annule toute requête en vol dès qu'une autre part sur le même chemin : une liste à l'écran et la lecture qu'une mutation fait avant d'écrire s'annulaient mutuellement. TanStack Query tient déjà ce rôle.
- **L'invalidation a lieu dans `onSettled`, pas `onSuccess`** : une lecture annulée reste sans données et sans requête en cours, donc une écriture en échec laisserait la liste sur « Chargement… » jusqu'à la navigation suivante.
- **Une écriture annule les lectures qu'elle invalide** (`useDerivedMutation`, `frontend/src/lib/mutations.ts`). Une lecture encore en vol au moment de l'écriture résout avec des données d'avant, et TanStack Query la réutilise au lieu d'en lancer une seconde : l'invalidation qui suit est satisfaite par une réponse plus ancienne que l'écriture, et la ligne créée reste invisible. Toute nouvelle mutation passe par ce helper.
- **Les parcours tournent un fichier à la fois** (`fileParallelism: false`). En parallèle ce sont des iframes de même origine, donc un même `localStorage`, et le `LocalAuthStore` de PocketBase suit les connexions faites dans les autres onglets : une connexion d'un fichier atterrissait dans le client d'un autre. Mesuré à un échec sur six ; 8 exécutions vertes en sérialisé, pour une vingtaine de secondes de plus.
- Le harnais laisse passer la **sortie d'erreur de PocketBase** : un hook qui échoue était indiscernable d'un hook qui ne fait rien.
- Formatage des dates : `Intl` suffit pour un nom de mois en français (`frontend/src/lib/dates.ts`). `date-fns` n'entrera que le jour où il faudra vraiment calculer sur des dates.

## Déploiement

- **La cible est Dokploy sur un VPS Hetzner, pas Fly.io.** Les specs techniques ont été
  alignées le 29/08/2026 (§1, §2.2, §2.3, §6, §7) et ne mentionnent plus Fly.io. Raison du
  changement : un volume Fly est un NVMe local non répliqué, donc la durabilité repose de
  toute façon entièrement sur Litestream, et la plateforme gérée n'achète rien à une
  application mono-conteneur qui ne peut pas se répliquer. Le VPS rend surtout l'exercice
  trimestriel de restauration banal — une commande locale au lieu d'une machine à
  provisionner.
- **Déploiement de type « Docker Compose », jamais « Application ».** Dokploy fait tourner
  Docker Swarm, dont l'ordonnanceur raisonne en répliques ; SQLite n'admet qu'un écrivain.
  Compose tient le mono-instance par construction, pas par convention.
- **Protéger `/_/` ne protège pas l'authentification.** La console est une page ; `/api/collections/_superusers/auth-with-password` est la porte, et un attaquant qui connaît l'API ne visite jamais la page. Cloudflare Access devant `/_/` réduit la surface de l'interface, pas celle du mot de passe. C'est pourquoi le hook de démarrage **active la limitation de débit** de PocketBase, livrée désactivée : ses règles par défaut plafonnent l'authentification à deux tentatives par trois secondes. Mesuré le 29/08/2026 — la deuxième tentative reçoit un 429 au lieu d'un 400.
- **Un déploiement Compose chez Dokploy ne reçoit aucune étiquette Traefik automatiquement**, contrairement au type « Application » : le routeur se déclare dans `deploy/compose.yml`, et le conteneur doit rejoindre le réseau externe `dokploy-network`. Sans les deux, le domaine résout, le TLS se termine, et **tout renvoie le 404 par défaut de Traefik** — 19 octets de `text/plain`, à ne pas confondre avec celui de PocketBase, qui répond du JSON. Un 502 dirait « conteneur mort », un 404 dit « aucune route ». Mesuré au premier déploiement réel, le 29/08/2026. `APP_DOMAIN` porte le domaine nu, `APP_URL` le même avec son schéma.
- **Aucun middleware Traefik n'est nommé dans les étiquettes.** Référencer un middleware inexistant met le routeur en erreur et fait retomber le HTTP en 404 — ce qui casse le défi ACME et, derrière un proxy qui parle en clair à l'origine, casse le site.
- **Le volume est nommé, pas monté depuis un chemin hôte.** Dokploy efface les bind mounts
  en chemin absolu à chaque déploiement — la base disparaîtrait au _second_ déploiement,
  donc le jour où il y a quelque chose à perdre.
- **L'image se construit sur le serveur** (choix assumé plutôt que `ghcr.io`). Le
  `Dockerfile` doit donc exécuter `pnpm install` puis `pnpm build` : `pb_public/` et
  `pb_hooks/lib/` sont gitignorés. Contrepartie mesurable : le build est le pic de mémoire
  de la machine et survient pendant que PocketBase sert — prévoir du swap sur 4 Go.
- **Litestream lance PocketBase, il ne tourne pas à côté** (`litestream replicate -exec`).
  Un sidecar peut mourir en silence et laisser la base servir sans réplication : rien n'a
  l'air anormal jusqu'à la restauration.
- **La restauration est le chemin de démarrage ordinaire.** L'entrypoint fait
  `litestream restore -if-db-not-exists -if-replica-exists` avant de servir : une machine
  qui démarre sur un volume vide se restaure seule, et le chemin est donc exercé à chaque
  déploiement neuf plutôt qu'une fois par trimestre.
- **Le SMTP de Resend passe par le port 587, pas 465.** Mesuré le 29/08/2026 depuis deux réseaux : les deux ports en TLS implicite (465, 2465) **expirent sans répondre**, les trois en STARTTLS (25, 587, 2587) répondent. Le symptôme en production était `dial tcp …:465: connect: connection timed out` — un délai d'attente, donc rien qui ressemble à une erreur, et un mail qui n'arrive jamais. `SMTP_PORT` vaut 587 par défaut dans le hook, qui en déduit `tls`.
- **Attribuer une panne réseau au bon coupable demande de la mesurer des deux côtés.** J'avais annoncé un blocage SMTP sortant de Hetzner avec assurance ; le port 465 s'est révélé muet depuis ma machine aussi, sur un réseau où même le port 25 passe. La cause n'était pas l'hébergeur. Un `connection timed out` ne dit pas _qui_ filtre.
- **Le bucket est chez Hetzner, donc chez le même fournisseur que le serveur** (décidé le
  29/08/2026, pour garder la réplication à l'intérieur du datacentre). La conséquence est
  à connaître : Litestream couvre toujours la perte du disque et de la machine, mais plus
  la perte du **compte**, qui emporterait le serveur et la sauvegarde ensemble. Endpoint
  `https://<région>.your-objectstorage.com`, régions `fsn1`, `nbg1`, `hel1` — vérifiées
  joignables le 29/08/2026. Couvrir le cas du compte demanderait une copie périodique
  ailleurs, jamais un second Litestream : deux réplications sur la même base se marchent
  dessus.
- **Litestream 0.5 n'a pas la forme de 0.3**, et les deux différences cassent au premier
  build : la configuration prend un `replica:` **singulier** là où 0.3 prenait un tableau
  `replicas:`, et les artefacts s'appellent `litestream-0.5.16-linux-x86_64.tar.gz` — sans
  `v` devant la version, et `x86_64` au lieu de `amd64`. Les quatre URL (deux binaires,
  deux architectures) ont été vérifiées en HTTP 200 le 29/08/2026.
- **Le SMTP de PocketBase vit en base, pas dans ses options.** Un conteneur qui démarre sur
  un volume vide sert donc avec le mail désactivé et des liens de réinitialisation pointant
  sur `localhost`, puisque le modèle construit son lien depuis `{APP_URL}`.
  `pb_hooks/apply_env_settings.pb.js` rejoue les réglages depuis l'environnement **à chaque
  démarrage** : c'est ce qui fait de la rotation de la clé Resend un redémarrage et non un
  nouveau fichier de migration. Le hook n'est **pas défensif** — une production qui démarre
  avec la récupération de compte silencieusement cassée est pire qu'un conteneur en échec.
  Sans `APP_URL` ni `SMTP_HOST` il ne fait rien, et c'est ce qui laisse le développement
  local et les parcours pointer vers Mailpit.
- **PocketBase sert `manifest.webmanifest` en `text/plain`** : la table MIME de Go ignore
  cette extension et l'image Alpine n'a pas d'`/etc/mime.types`. Mesuré le 29/08/2026 dans
  le conteneur réel. Le reste est correct (`sw.js` et les assets en `text/javascript`, le
  CSS, les PNG). Les navigateurs analysent le manifeste sans exiger son type, donc
  l'installabilité n'est probablement pas atteinte — mais la vérification de l'étape 7
  portait sur le serveur de développement, pas sur celui de production.

## Contraintes d'outillage

- **TypeScript est figé en 6.0.3**, alors que 7.0.2 (réécriture Go) est le `latest`. Raison : typescript-eslint 8.67 déclare `typescript: >=4.8.4 <6.1.0` et ne supporte pas encore TS 7. Monter TS 7 signifierait perdre le lint type-aware. À réévaluer quand typescript-eslint suivra.
- `allowImportingTsExtensions` est activé : les imports portent leur extension (`./currency.ts`). Le build passe par Vite, jamais par `tsc`.
- Prettier ignore `docs/` : la mise en forme des specs est rédigée à la main, pas générée.

## Modèles de données particuliers

Trois relations dans `transactions` méritent attention car elles encodent des cas métier distincts :

- `transfer_ref` — virement entre comptes : une seule opération saisie, débit + crédit liés, **qui ne compte pas comme une dépense** dans les budgets et rapports (`CPT-05`).
- `split_parent` — transaction scindée sur plusieurs catégories (`TRX-08`).
- `recurring_rule` — transaction générée par une règle récurrente.

Les `debts` ont une `direction` (`je_dois` / `on_me_doit`) : le module gère aussi l'argent qu'on doit à l'utilisateur (`DET-02`). Le taux d'intérêt est facultatif (dettes informelles, tontines) mais les échéanciers avec intérêts sont pleinement supportés.

## Versions figées

Les versions du tableau `docs/specs-techniques-budget.md` §2 ont été vérifiées au 09/08/2026 et font foi. Points de vigilance :

- **PocketBase est en pré-1.0** (0.39.3) : figer la version en production, lire les notes de migration avant toute montée.
- **Litestream 0.5+** utilise le format LTX — ignorer les tutoriels 0.3.
- **Tailwind 4** se configure en CSS, il n'y a plus de `tailwind.config.js`.

## Commandes

Toutes se lancent depuis la racine ; le workspace est géré par pnpm.

```bash
pnpm install            # requiert Node >= 24
pnpm services:install   # récupère les binaires épinglés PocketBase et Mailpit dans bin/
pnpm pb:dev             # démarre PocketBase sur 127.0.0.1:8090
pnpm mailpit:dev        # boîte SMTP locale : SMTP 1025, interface 8025
pnpm dev                # serveur de développement Vite
pnpm domain:build       # bundle du domaine vers pb_hooks/lib/domain.cjs
pnpm icons:build        # régénère les icônes PWA depuis leur script
pnpm build              # domaine puis frontend vers pb_public/
pnpm typecheck          # tsc --noEmit sur chaque paquet, en parallèle
pnpm lint               # ESLint, avec règles type-aware
pnpm format             # vérification Prettier (format:write pour corriger)
pnpm test               # les deux projets Vitest
pnpm test:domain        # scénarios métier seuls (rapides, node)
pnpm test:journeys      # parcours navigateur seuls (chromium)
```

Pour un seul scénario : `pnpm test:domain -t "formats it as whole francs"`.

Le browser mode exige chromium, à installer une fois :
`pnpm --filter @budget/frontend exec playwright install chromium`.

Les parcours démarrent eux-mêmes leurs services (`frontend/test/global-setup.ts`, en
`globalSetup`), avec un `pb_data` temporaire supprimé en fin de run — d'où le prérequis
`pnpm services:install`. Ports dédiés pour ne pas percuter le dev : PocketBase **8091**,
Mailpit SMTP **1026** et interface **8026** (contre 8090 / 1025 / 8025 en développement).

Le harnais assemble le répertoire de hooks dans un temporaire : `pb_hooks/` de production
**plus** les sondes de test de `frontend/test/pb_hooks/`. Les vrais hooks sont donc chargés
par les parcours, et les sondes ne partent jamais en production.

Le SMTP de PocketBase vit en base, pas en ligne de commande : le `globalSetup` crée un
superuser puis pointe les réglages vers Mailpit via `PATCH /api/settings`.

À venir avec les étapes suivantes : démarrage de PocketBase en local, `fly deploy`, et `litestream restore` (à tester une fois par trimestre).
